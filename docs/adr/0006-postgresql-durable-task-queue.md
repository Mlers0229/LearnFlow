# ADR-0006：使用 PostgreSQL 实现持久异步任务队列

- 状态：Accepted
- 日期：2026-08-21
- 决策人：LearnFlow 维护者

## 背景

计划生成已经接近同步 HTTP 请求的 90 秒预算。后续批量 Embedding、索引与评测也需要持久重试、取消、超时回收和故障后恢复。当前规模尚不足以证明引入 Redis、RabbitMQ 或 Kafka 的额外运维成本合理。

## 决策

1. 第一阶段使用 PostgreSQL `async_task` 表作为任务事实源，由 Spring Boot 提交、领取和更新任务。
2. Worker 使用 `FOR UPDATE SKIP LOCKED` 在短事务中领取任务；执行模型调用时不得持有行锁或数据库事务。
3. 采用至少一次投递语义。业务执行器必须使用任务 ID 或幂等键阻止重复业务写入。
4. 任务状态限定为 `PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED`。`FAILED` 且尝试次数达到上限的任务构成死信集合，只允许管理员显式重放。
5. 运行中任务使用租约；实例退出或失联后，过期租约由其他实例回收。任务同时具有独立的整体截止时间。
6. 请求 Payload 只用于执行，不写入日志；成功或取消后立即清除，失败任务仅在受限死信保留期内保存以支持重放。结果只保存业务资源引用，不复制完整计划内容。
7. 本阶段只迁移已有且确实超过同步预算的计划生成。批量 Embedding、持久索引和批量评测在 M3 建立真实实现后接入同一任务适配层。

## 选型门槛

出现以下任一情况时重新评估独立消息中间件：

- PostgreSQL 任务轮询持续消耗超过数据库容量预算的 10%。
- 稳态待执行任务超过 10,000，或任务领取 P95 超过 1 秒。
- 需要跨区域投递、复杂路由、超高吞吐或独立扩缩容，而数据库队列无法满足。

## 取舍

该方案复用现有 PostgreSQL、Flyway、备份和权限体系，减少新的故障面。代价是吞吐和路由能力弱于专用消息中间件，因此任务访问集中在适配服务中，不让业务代码依赖具体领取 SQL。

## 风险

- 长事务会拖累数据库：领取和状态更新必须短事务提交后再调用 Agent。
- Worker 崩溃会导致重复执行：租约回收与业务幂等约束必须同时存在。
- Payload 包含用户目标：终态立即清除，错误信息只保存分类和限长摘要。

## 回滚

关闭 `LEARNFLOW_TASKS_ENABLED` 后，Worker 停止领取新任务；现有同步 `/api/plan` 继续可用。未来迁移到专用消息中间件时保留任务 API 和状态契约，只替换领取适配器。
