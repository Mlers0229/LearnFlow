# ADR-0002：身份认证与会话策略

- 状态：Accepted
- 日期：2026-08-21
- 决策人：LearnFlow 维护者

## 背景

当前登录接口只返回用户信息，浏览器将用户和角色写入 `localStorage`，API 又接受客户端传入的 `userId`。任何调用方都可以伪造身份或管理员角色。

## 决策

1. 第一版生产认证使用自建短期 JWT Access Token 和可轮换 Refresh Token。
2. Access Token 只保存在浏览器内存，默认有效期 10 分钟；Refresh Token 通过 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie 传递，默认有效期 14 天。
3. Refresh Token 仅以哈希形式持久化，记录用户、会话、过期时间、撤销时间和轮换链。刷新时执行一次性轮换；检测到旧 Token 重放时撤销整条会话链。
4. Spring Security 验证签名、`iss`、`aud`、有效期和用户状态，并将用户 ID 与角色写入安全上下文。
5. 服务端只信任安全上下文中的用户身份。请求体、查询参数中的 `userId`、用户名和角色字段将被删除或忽略。
6. 角色首版固定为 `student` 和 `admin`，管理接口使用方法级授权；普通资源同时执行资源归属校验。
7. 登录失败必须限流；密码继续使用 BCrypt，并增加密码长度与常见弱密码约束。
8. 认证模块通过接口隔离 Token 签发和用户映射，后续可以迁移到 OIDC，而不改变业务服务的 `CurrentUser` 使用方式。

## 取舍

- 自建 Token 能复用现有账号表、控制首轮范围，但需要自行实现轮换、吊销、密钥轮换和登录限流。
- OIDC 在多客户端或企业身份接入时更合适；当前没有确定的身份供应商，因此不在 M1 强制引入。

## 风险

- XSS 可窃取内存中的 Access Token，因此前端仍需 CSP、输出转义和依赖扫描。
- Cookie 刷新接口需要 CSRF 防护；使用 SameSite、严格 Origin 校验和刷新端点 CSRF Token/双提交策略。
- JWT 签名密钥泄漏会影响全部会话，必须由 Secret Manager 注入并支持 `kid` 轮换。

## 回滚

认证上线采用兼容窗口和功能开关。若新认证出现阻断，可回滚应用到上一版本；不得长期恢复为信任客户端身份。数据库中的 Refresh Token 表允许保留，回滚版本不会读取它。
